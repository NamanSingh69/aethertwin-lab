A robotics lab, measured in 3D from a hand-pushed cart.

AetherTwin scans a room with a Unitree L2 LiDAR and a depth camera on a Raspberry Pi 5, streams the raw data over Wi-Fi to a laptop GPU, and builds a 3D twin with tracking, risk fields and safe paths that you watch in a browser. This page reports what has been measured, and what has not.

02

How it works

From a laser sweep to a scene in the browser, in eight stages.

  1. 1

    Capture

    A Raspberry Pi 5 on the cart reads the LiDAR, its IMU and the RGB-D camera, and forwards raw data only.

    ingestion/capture_node.py
  2. 2

    Transport

    Our own raw-sensor protocol over Wi-Fi: mutual HMAC authentication, a MAC and a strict sequence number on every message.

    ingestion/raw_transport.py
  3. 3

    Sync and deskew

    LiDAR, IMU and camera go on one timeline; then each point is moved back to where it was, using IMU integration.

    slam_and_twin/imu_deskew.py
  4. 4

    Register

    ICP scan registration with a pose graph builds the map. A parked rig localizes once against the twin, then holds.

    slam_and_twin/
  5. 5

    Map and twin

    Log-odds occupancy and TSDF volumes, then a Poisson mesh for display. Unknown space is never assumed free.

    slam_and_twin/log_odds_octomap.py
  6. 6

    Perceive and track

    A sparse point network labels voxels (trained on synthetic data only, so far); a 9-state Kalman tracker follows people and objects between frames.

    perception_ml/
  7. 7

    Risk and plan

    A directional risk field with time-to-collision and protected zones feeds an A* and B-spline planner. Simulation only, today.

    tracking_and_navigation/
  8. 8

    Studio

    A FastAPI service streams a versioned binary scene protocol to a React and Three.js studio with streamed map tiles.

    command_center/ · web/src/scene/

The reasoning behind each stage, with four small interactive labs, is in the step-by-step explainer.

03

The rig and the studio

Low-cost sensors, one laptop, no cloud.

LiDAR
Unitree 4D LiDAR L2 with built-in IMU, mounted upright, window 9.0 cm above the floor
Depth camera
Orbbec Gemini 336L at 640 × 400, 21 cm in front of the LiDAR
Capture node
Raspberry Pi 5 on the cart; LiDAR on Ethernet, camera on USB
Compute
Windows laptop with an RTX 4070 Laptop GPU, reached over its own Wi-Fi hotspot
Status board
ESP32-S3 for an LED halo; firmware built, LEDs not yet fitted
Platform
22.9 × 15.2 cm wheeled cart
  • Layers for the measured twin, semantic voxels, tracks, safe trajectory, risk hotspots and protected zones.
  • Scrub, pause and step the recording frame by frame.
  • Instanced rendering, streamed map tiles and automatic quality tiers.
  • Keyboard shortcuts, a help overlay and automated accessibility checks.
  • Visual effects are labelled presentation-only inside the interface.

04

Engineering practice

Built to be checked, not just shown.

  1. Evidence before claims

    Every figure in the interface and the documents carries what it measures and its source file. The studio shows “Hardware not tested” until a measured run says otherwise.

  2. Speed-ups that cannot change results

    Each optimisation ships with a test that runs a verbatim copy of the old code and demands identical output. That is how 381 ms became 240 ms in rehearsals without a behaviour change.

  3. Tested end to end

    More than 700 Python tests, web unit tests, and browser runs against a mock service, a live simulated service and this static site, from one local CI command.

  4. Secure by default

    Authenticated sensor transport, a strict content security policy, and a replay exporter that fails if an address, path or device identifier leaks into public files.

  5. Reproducible environments

    Hash-locked dependencies for Windows, Ubuntu and CUDA. Python 3.12, PyTorch and Open3D on the back end; React 19, TypeScript and Three.js on the front.

  6. A journal of every change

    About fifty change cycles are logged with a hypothesis, a failing test first, and a keep-or-revert decision. Reverts are kept as results.

05

Where it goes next

From a pushed cart to a robot that maps the lab by itself.

Everything after the first row is planned work, not a result. Each phase is defined by the measurement that ends it.

  1. Done

    Sensing rig and live pipeline

    Cart, authenticated Pi-to-laptop stream, a twin from a stationary recording, parked localization, a 15-minute live run, the browser studio and this public replay.

    The results above

  2. Phase 1 · next

    A complete, calibrated twin of the lab

    Camera-LiDAR calibration with a target; a slow moving scan with loop closure, so the twin covers the whole room in colour; then a 30-minute verified run.

    Landmark error against a tape, as percentiles; world-to-display latency

  3. Phase 2

    Localization while moving

    Replace the fixed scan window with LiDAR-inertial odometry: an IMU-propagated state registered against a persistent local map, cross-checked offline against open-source baselines.

    Trajectory error on return-to-start loops

  4. Phase 3

    An autonomous rover that reaches a goal

    Motorize the cart: wheel odometry, a velocity controller, a hardware stop. A* routes on the twin; a local planner avoids live obstacles using the occupancy map and risk field. Click a destination in the studio and the robot drives there.

    Goal success rate, clearance kept, stops near people

  5. Phase 4

    Self-scanning, and a twin that stays current

    Frontier-based exploration sends the robot to unmapped space until the room is covered, with nobody pushing. Repeat patrols detect what changed and update the twin.

    Coverage over time; change-detection precision

  6. Phase 5

    Real time on the GPU

    Move deskew, voxelization and occupancy onto GPU-resident tensors in one process, towards the 35 ms target. How close it gets is not known until it is measured.

    Per-stage GPU timings on the real rig
